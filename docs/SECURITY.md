# Security policy and threat model

This library handles a short PIN and may be used by a host application to gate access to a screen. It is a UI and local credential-verification component, not a certified authentication product.

## 1. Security boundary

The library does not replace the Android operating-system lock screen, encrypt host application data, protect files or backups, provide server-side identity, prevent a rooted-device owner from inspecting memory, or guarantee that every protected screen in the host application is gated.

The host application is responsible for enforcing authorization after the activity returns `Activity.RESULT_OK`.

## 2. Four-digit PIN entropy

A four-digit decimal PIN has only 10,000 possible values. It is convenient for a keypad but weak as a standalone secret.

PBKDF2 makes offline guessing more expensive than a fast unsalted digest, but it cannot increase the number of possible PINs. Applications protecting sensitive data should consider longer credentials, platform authentication, and an authorization design appropriate to the data's risk.

## 3. Previous SHA-256 storage

Earlier versions stored an unsalted SHA-256 digest. SHA-256 is designed to be fast. A four-digit PIN can be exhaustively tested against such a digest with little effort.

New PIN credentials must not use plain SHA-256, MD5, or another fast unsalted hash as a password-storage mechanism.

## 4. Current PBKDF2 storage

New PIN credentials use:

- A 16-byte random salt generated by SecureRandom.
- PBKDF2WithHmacSHA1.
- 120,000 iterations.
- A 256-bit derived output.
- A byte-wise final comparison using `MessageDigest.isEqual`.

The salt and verifier are stored in private SharedPreferences. The raw PIN is not written to persistent preferences.

The iteration count is an explicit compatibility and performance trade-off. Revisit it as device performance and Android platform support evolve. Benchmark on low-end supported devices before raising it substantially.

## 5. Legacy credential migration

When the old SHA-256 key is present and no PBKDF2 verifier exists, the library checks the entered PIN against the legacy digest. If it matches, a new salt and PBKDF2 verifier are generated and persisted, and the legacy key is removed.

A failed PIN attempt does not modify the credential. A malformed or incomplete current verifier fails closed.

## 6. Logging and telemetry

A PIN or partial PIN must never appear in logs, analytics, crash reports, notifications, clipboard history, saved instance state, or remote diagnostics.

The `PinLockListener.onPinChange` callback includes the intermediate PIN. Consumers registering their own listener must treat that argument as secret material. Log only non-sensitive state such as the number of digits entered.

## 7. SharedPreferences and device compromise

Private SharedPreferences are protected by Android's application sandbox, but they are not hardware-backed storage. A rooted, compromised, instrumented, or debug-enabled device may expose the preference file or runtime state.

For applications that encrypt local secrets, use a separately reviewed Android Keystore design. Do not assume the PBKDF2 verifier is an encryption key or that this library encrypts the host application's data.

## 8. Fingerprint handling

The fingerprint template remains managed by Android. The application receives authentication callbacks, not a fingerprint image or template.

The activity checks hardware, enrollment, permission, and secure-lock-screen state. It cancels authentication when paused and ignores callbacks after cancellation.

The current integration uses the deprecated platform FingerprintManager API. It should be migrated to AndroidX Biometric and BiometricPrompt in a future major version. Do not claim that this implementation supports face recognition or every biometric modality.

## 9. Attempt throttling

A persistent failed-attempt lockout is not implemented. Incorrect PIN entries reset the keypad but do not create an escalating wait period or durable attempt counter.

A local counter can be bypassed by clearing app data or reinstalling the application. A production design should consider platform authentication, longer secrets, server-side risk controls, and rate limiting appropriate to its threat model.

## 10. Host application checklist

1. Keep EnterPinActivity non-exported.
2. Require `Activity.RESULT_OK` before continuing.
3. Check the expected request code and app state.
4. Do not store raw PIN values in a second location.
5. Do not log the intermediate PIN callback.
6. Protect the underlying data independently.
7. Review backup and device-transfer behavior.
8. Re-authenticate before high-risk actions.
9. Use HTTPS and server-side authorization for remote resources.
10. Avoid claiming compliance or certification based only on this library.

## 11. Vulnerability reporting

Do not publish secrets, personal information, or detailed exploit instructions in a public issue. Use GitHub's private vulnerability reporting feature when available.

Include the affected commit, Android version, device type, impact, reproduction steps, and relevant logs with secrets removed.

## 12. Security release checklist

- [ ] Correct PIN succeeds.
- [ ] Incorrect PIN fails.
- [ ] New salt is generated for each credential.
- [ ] Invalid PIN formats are rejected by utility methods.
- [ ] Legacy SHA-256 credentials migrate only after successful verification.
- [ ] Malformed stored verifier data fails closed.
- [ ] No raw PIN or partial PIN appears in logs.
- [ ] Fingerprint authentication is cancelled on pause.
- [ ] Fingerprint absence does not block PIN entry.
- [ ] Host app checks the exact successful result.
- [ ] Manifest exported settings are reviewed.
- [ ] Dependencies and release artifacts are reviewed.
